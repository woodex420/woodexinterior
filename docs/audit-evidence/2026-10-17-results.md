# Audit behavior-probe evidence — 17 October 2026 PKT

## Scope and safety

Ran against the existing local application in the sandbox PHP 8.4 runtime. Pest's existing `RefreshDatabase`/`TestCase` seeds a **fresh in-memory SQLite database**, `APP_ENV=testing`, `QUEUE_CONNECTION=sync`, array sessions/cache, fake local artifact storage, fake email/notifications/WhatsApp and blocked stray HTTP requests. No production DB/provider call, application feature edit or active-preview DB restore was performed.

Source snapshot: [2026-10-17-behavior-probes.php.txt](2026-10-17-behavior-probes.php.txt). It was copied **only into the temporary runtime**, not the repository's normal test suite, as `tests/Feature/AutomationAuditProbeTest.php`.

These probes deliberately **assert undesirable current behavior** so the observations are reproducible. Passing means a finding was reproduced, **not that a defect was fixed**. When implementing repairs, convert them to desired-contract regression tests and include additional actual MySQL concurrency tests. Do not add these assertions unchanged to production CI.

## Observations and limits

| Finding | Exercised boundary | Exact evidence | Not claimed |
|---|---|---|---|
| F01 | Livewire payment form as an authorized accountant | `save` reports no validation errors; payment belongs to client A, allocation targets B's invoice; invoice becomes paid. | Anonymous exploit or production data damage. |
| F02 | `AllocatePayment` action with explicit target | Void invoice becomes paid. | That normal dropdown offers void invoices. Action must still enforce invariant. |
| F03 | `VerifyPayment` with two preloaded pending model instances | First receipt number is replaced by second; payment remains verified and has one allocation. | Concurrent MySQL execution or double allocation of money in this probe. |
| F04 | `RecordPayment` action with `input.allocations` | Requested newer invoice remains unpaid; oldest invoice gets sole allocation. | UI already provides complete manual allocation-map editor. |
| F05 | `RecordPayment` with target and excess | 15,000 minor units recorded; target consumes 10,000; second open invoice gets zero. | Desired credit policy independently confirmed; conflict is with D-85/current comments. |
| F06 | Correctly HMAC-signed HTTP webhook, two different inbound messages, then same payload replay | One message stored, second absent, second event failed, replay still one message. | Every single-message webhook fails; existing normal/replay tests pass. |
| F07 | Correctly HMAC-signed HTTP webhook with two read receipts | First message read; second still sent; both events processed. | Provider itself delivered the second message incorrectly. This is local batch handling. |
