## 1. What this plan is — and what it refuses to be

The three references are **workflow references, not stacks**. This is a Laravel 13 / Livewire 4 / SQLite OS with a
locked v1 frontend and a working double-entry ledger; it does not become a NestJS + React monolith to look like
Gauzy. What is taken is the *shape of the work*: the money-out loop Gauzy calls *Invoices Received / Expenses /
Income*, the contact ladder *visitor → enquiry → customer → client*, Search Console as a **tool server** (the
mcp-gsc pattern) rather than a documentation card, and the "assistant over real records" pattern from
awesome-llm-apps.

Three rules are unchanged from the standing directive:

1. **No screen may claim a result it cannot produce.** A connector without a key says so and names the key.
2. **No code before the decision is locked.** This document is the plan; nothing below is built yet.
3. **Every slice ships the same way:** audit → code → tests → live proof on 33143 → docs → short report. No slice is
   "done" on a screenshot alone.

## 3. What is taken from each reference

| Reference | Taken | Not taken (and why) |
|---|---|---|
| **[Ever Gauzy](https://github.com/ever-co/ever-gauzy)** | The money-out workflow: **Received Invoices** (vendor bills with paid-status and value), **Income**, **Expenses**, **Recurring Expenses**, the four-way contact model (**Visitors / Leads / Customers / Clients**), proposals as a first-class stage, and a dashboard that shows income vs expenses — not just receivables | NestJS/React stack, multi-tenant organisations, payroll, ATS, time tracking, inventory/procurement, i18n and multi-currency. Each is a product of its own; none is in this OS's job |
| **[mcp-gsc](https://github.com/AminForou/mcp-gsc)** | Search Console exposed as **MCP tools** — search analytics query, sitemap list, URL inspection — registered into the MCP layer that already exists (`McpTools`, `McpAccessToken`, `McpHttpController`), reading the owner's property through the existing `GoogleOAuth` / `GoogleConnection` scaffold | Scraping Search Console without OAuth, or a second Google auth flow |
| **[awesome-llm-apps](https://github.com/shubhamsaboo/awesome-llm-apps)** | The **assistant over real records** pattern: a drawer that answers a question by running a small set of whitelisted queries and cites the rows it read ("3 invoices are overdue: INV-…, INV-…") | Agent frameworks, autonomous tool loops with write access, anything that answers without reading the database |

**The line that does not move:** no LLM answer may invent a number. The assistant either runs a query and cites it,
or says it cannot answer from the data.

## 4. The slices

Ordered by value per unit of risk. Each has an acceptance test that a live page must pass.

### Slice I — Money out, and a true P&L (Accounts) · ✅ done 26 Oct (`a577063`)
The screenshot the owner sent is exactly this gap: a received-invoices table with vendor, dates, value and paid
status. Nothing on the money-out side exists today.

| Piece | What ships |
|---|---|
| **Vendors** | A supplier register (name, phone, email, NTN/STRN, payment terms, default expense account, active) under Accounts |
| **Bills — "Invoices Received"** | Vendor bill: number, vendor, bill date, due date, lines, tax, total, paid status; statuses draft → received → part-paid → paid → void; attachment path; each bill posts **Dr expense (5xxx/1200/1300) / Cr Accounts payable 2010** on posting, and each payment posts **Dr 2010 / Cr cash or bank** |
| **Estimates received** | A vendor quotation attached to a bill before it is received (the Gauzy "estimates received" page), same vendor record |
| **Expenses** | One-off operating expenses outside a project (rent, fuel, fees…) — date, vendor optional, category → account, amount, paid-from (cash / bank / payable), note, receipt path; posts to the ledger through `PostJournalEntry` |
| **Recurring expenses** | Template + cadence (monthly / quarterly / yearly) + next run + end date; a scheduler command that raises the next expense and posts it, exactly mirroring the recurring-invoice pattern |
| **Other income** | Small income entries to 4090 (or a chosen income account) — same shape as expenses, opposite direction |
| **Project cost posting** | The expenses already captured on a project **post to the ledger** (Dr the project's cost account / Cr payable or cash), and the project screen shows *cost to date vs quoted cost vs invoiced* — job profit becomes real |
| **P&L** | `/admin/accounts/profit-loss`: income accounts minus expense accounts over a date range, with the same presets and the same honest empty state as the trial balance; net profit line; links to the journal behind every figure |
| **AP aging** | Unpaid bills by age bucket (current, 1–30, 31–60, 61+), mirroring the AR receivables screen |

**Needs owner approval:** 4 new tables (`vendors`, `bills`, `bill_items`, `expenses`) plus `recurring_expenses` and two
nullable columns on `project_expenses` (account, posted journal id). No existing table is altered destructively and no
row is deleted.
**Acceptance:** post a bill → trial balance still balances and AP shows the amount; pay it in two parts → AP nets to
zero, bank/cash moves; raise a recurring rent → the scheduler creates and posts exactly one expense per period;
enter a project cost → P&L expense rises and the project shows the margin; P&L income − expense = net profit and
equals the ledger movement for the range.

### Slice J — The contact ladder (CRM) · ✅ done 26 Oct
**Clients** tab (`contacts.is_client = true`) and **Customers** (a contact with at least one accepted quotation or
project) as saved views over the same record, with counts, LTV and last activity; **Visitors** comes from the only
honest source we have — enquiries with `source = website`/`estimator` plus site visits — labelled as enquiries, not
as analytics we do not collect. Contact 360 gets the money card, projects, quotations and the timeline in one page.
**No schema change.** Acceptance: the four tabs show disjoint, correct sets over the demo data, and a contact that
becomes a client moves tab by itself.

### Slice K — Sales: proposals stage and forecast (Sales) · ✅ done 26 Oct
A quotation gains an explicit **Proposal** state in the pipeline it already has (draft → proposal → sent → accepted),
a board over quotations by stage with value and weighted forecast, and "estimates received" surfaced next to vendor
bills. Reads the existing tables; no new money paths. Acceptance: dragging a proposal to *sent* writes the same
status the quote screen shows, and the forecast equals Σ(value × stage probability) to the rupee.

### Slice L — Telegram that attaches (System) · ✅ done 26 Oct
A real pairing flow: the Security & Telegram page shows a **QR generated on our server** (no third-party image
service) encoding `https://t.me/<bot>?start=<one-time code>`, a copyable link, the code's expiry countdown, and the
live state (*waiting → linked as @handle → last message received*). One tap on the phone opens Telegram and the bot
links itself; nothing is retyped. Plus a **connection health card** that names the exact failing step (token missing /
webhook not set / webhook set but no update in 24 h / bot blocked by the user) instead of a generic "not connected".
**No schema change** (`telegram_links` already carries the code, expiry and timestamps).
Acceptance: a fresh code renders a scannable QR that decodes to the deep link; the webhook receives `/start CODE` and
the page flips to *linked* with the chat id without a reload; an unconfigured bot shows the missing key by name.

### Slice M — The assistant drawer, and marketing attribution · ✅ done 26 Oct
A drawer available on every admin page (the owner's second screenshot): questions are answered by a small, fixed set
of **read-only queries** over invoices, bills, projects, leads and tasks, each answer citing the records it read;
keyless mode answers the whitelisted questions deterministically, OpenAI/Anthropic improve the phrasing only. Alongside
it, marketing gains **source → enquiry → won value** attribution using `leads.source` (no ad spend until Meta is
approved). Acceptance: "what is overdue?" returns the same rows as `/admin/invoices?tab=tracking`, with numbers that
match the page; a question outside the whitelist says so.

### Slice N — Search Console over MCP (System) · **blocked on the owner's Google key**
The mcp-gsc pattern lands inside the existing MCP layer: tools `gsc.query`, `gsc.sitemaps`, `gsc.inspect` and a
Search Console screen reading clicks / impressions / position for the real property. Until `GOOGLE_CLIENT_ID` and
secret are supplied, the screen renders the *blocked* state naming the missing key — never sample data.

## 5. Order, and why

1. **I — money out + P&L.** It is the only slice where the books are currently *wrong* (costs outside the ledger), it
   matches the owner's screenshot, and every later report depends on it.
2. **L — Telegram QR.** Small, self-contained, fixes a complaint the owner made twice; ships inside a day of work.
3. **J — contact ladder.** Read-only views over existing data; makes CRM look like the reference without new schema.
4. **K — proposals and forecast.** Turns the quotation list into a pipeline the owner can steer by.
5. **M — assistant + attribution.** Needs I and J in place to have anything worth asking about.
6. **N — Search Console.** Code can ship earlier, but the screen stays blocked until the Google key exists.

**Blocked on the owner, unchanged:** Meta / LinkedIn app approval (marketing live proof), Google OAuth client
(Search Console, Gmail), AI provider keys (assistant phrasing), Telegram bot token in the server `.env` (pairing can
be built and tested with the fake gateway, but the live flip needs the real token), GitHub `workflows` permission.

## 6. Change control for every slice

* **Schema:** listed per slice and approved before the migration is written. Nothing destructive, rollback = revert.
* **Permissions:** new screens declare theirs; no role is widened silently — a mismatch is recorded and reported
  (the accountant / `accounts.view` finding from Slice H is still open for the owner's decision).
* **Tests:** every screen gets feature tests for the real path, the refusal path and the empty state; the suite count
  in `PROJECT_STATUS.md` is updated with each ship.
* **Proof:** live on 33143 with real domain actions, not tinker inserts; QA rows removed afterwards and sequences
  rewound.
* **Docs:** a `16_MASTER_TODO` step and a `31_DEEP_QA` block per slice; `PROJECT_STATUS.md` counts updated.
