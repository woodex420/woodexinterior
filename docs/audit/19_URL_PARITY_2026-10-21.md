## 5. Finding: the sitemap cache was not per host (fixed)

`SitemapController` caches the document (`Cache::remember('website.sitemap.'.md5($version))`) under a key built
from the newest file mtime, the page count and the newest `pages` row — **not the host**. The document itself holds
absolute URLs derived from the request (`url('/')`).

Reproduced in the sandbox:

1. A sitemap was built for the preview host and cached.
2. A request for `/sitemap.xml` was then handled with `Host: woodex.com.pk` and `APP_URL=https://admin.woodex.com.pk`;
   `url('/')` correctly answered `https://woodex.com.pk`.
3. The response still carried the **preview host's** URLs — the cached copy — and only `cache:clear` rebuilt it.

In production the same window exists between the public domain and the admin domain (`docs/06` sets
`APP_URL=https://admin.woodex.com.pk`): whichever host builds the sitemap first, the other is served that host's
URLs for up to a day. A sitemap of admin-domain URLs, served to Google, is a broken sitemap.

**Fix (applied):** the request's `getSchemeAndHttpHost()` is now part of the version that keys the cache, so each
host builds and keeps its own document. `CmsPageTest` gains *"it answers each host with its own sitemap, never the
copy another host cached"*: it builds the sitemap for `woodex.com.pk`, then asks as `admin.woodex.com.pk` and
expects each `<loc>` to carry the asking host. With the line removed the test fails on the second assertion; with
it, it passes.

Sandbox note: `tools/sandbox/preview-env.sh` deliberately sets `APP_URL=/` so assets stay root-relative behind the
preview proxy; that is why a freshly built sandbox sitemap can show `<loc>/</loc>`. It is a sandbox setting, not
the production behaviour (`url('/')` follows the request host there, as step 2 above shows).

## 6. The 36 redirects on the other instance

The screenshots came from a different instance that reports **36 redirects**; this workspace has **0**:

- `database/data/legacy-website.php` says the redirect map is empty since 17 Oct 2026 ("the owner asked for the
  complete site"), and lists no rules.
- The `wx_redirects` table is empty; neither `.htaccess` carries a `Redirect` rule.
- None of the 143 live sitemap URLs is a redirect — every one is a page.

So the 36 exist only in that instance's database and cannot be reconstructed from this repository. None of them
affects the sitemap result above. If any of those source URLs still has inbound links or rankings, they will 404
after a deploy that replaces the database; the only way to keep them is to export the rows from that instance and
import them **before** the deploy.

**Owner's answer: export them before deploy.** What is needed is the three fields each row carries —
`from_path`, `to_path`, `code` (plus `note` if any are annotated) — either copied from that instance's
**Admin → Website → Redirects** (`/admin/website/redirects`) or from its database:

```sql
SELECT from_path, to_path, code, note FROM redirects ORDER BY from_path;
```

Send that and every row is imported here and asserted to answer 301 to its target; the sitemap result above does
not change either way.

## 7. Error pages

The other instance has `404.html`, `500.html` and `503.html`; this workspace has none. That changes nothing that
was observed: a missing URL is answered by the app, not by the disk —

```
/furniture/        -> 404  <title>Page not found | Woodex Interior</title>
/nonexistent-page/ -> 404  <title>Page not found | Woodex Interior</title>
/about             -> 200  (the file; Apache adds the slash in production)
```

The 404 is `resources/views/errors/404.blade.php`, styled like the site. The three static files would only matter
if Hostinger served error documents from disk, and with the root `.htaccess` routing everything to Laravel it does
not.

**Verified:** the live sitemap set, file counts, status codes, titles, descriptions, canonicals, `noindex` flags,
`<h1>` counts, internal links, the app sitemap's contents, the 404 body, and the cache reproduction.

verified against the CMS export, plus one live page (the home) end to end.
